# MCP-001 — Servidor MCP gobernado para RestaurantOS

Fecha: 2026-10-30. Riesgo del runtime: R3 por autenticación, permisos, datos financieros,
inventario, concurrencia, migración e integración externa. Existe un scaffold local de fase A,
deshabilitado por defecto; no está publicado, desplegado ni configurado. Este paquete no autoriza
despliegue, migración, secretos, configuración, canary ni datos productivos.

## 1. Objetivo y resultado

Construir un solo servidor MCP remoto, neutral al proveedor, para que varios bots lean y registren
intenciones controladas en Kiwi sin acceso directo a PostgreSQL, sesiones humanas, credenciales
maestras o rutas genéricas. MCP reutiliza la autoridad de Agent Tools y servicios canónicos.

Resultado por fases:

1. **A — Lectura canary:** `/mcp` default-off, OAuth resource server, manifiesto explícito y las
   dieciséis lecturas, con un cliente Administrador y una sucursal.
2. **B — Multibot:** identidades, credenciales, revocación, capacidades, sucursales y auditoría
   independientes por bot, incluso si comparten perfil.
3. **C — Escritura mediada:** sólo propuestas de catálogo/insumo/receta y compra `DRAFT`, con
   idempotencia y recuperación. Nunca aplicación o confirmación directa.

## 2. Marco y decisiones rectoras

| Autoridad | Contrato MCP-001 |
|---|---|
| PRD | PRD-FR-301..304 y PRD-NFR-033; conserva PRD-FR-269..273/NFR-032 |
| SDD/ADR | SDD §72 y SDD-ADR-049; Agent Tools y `AgentToolsService` compartido |
| BDD | BDD-FEAT-160; BDD-SC-811..822 |
| TDD | TDD-TS-163; TDD-TC-481..493 |
| Trazabilidad | Filas nuevas en `docs/05-matriz-trazabilidad.md`, estado `Disenado` |

Invariantes:

- prompt/body/`_meta` no deciden organización, perfil, capacidades o branches;
- cada llamada revalida identidad, versión, capacidad y sucursal;
- no existe herramienta genérica, SQL, URL o exposición automática de APIs;
- REST y MCP invocan el mismo servicio en proceso, sin HTTP interno ni lógica duplicada;
- las escrituras permanecen `READY_FOR_REVIEW` o `DRAFT` y no producen efectos financieros,
  inventario, costo, permisos ni caja;
- timeout no equivale a éxito; replay usa la misma key y hash; recuperación reautoriza;
- revocación bloquea nuevas llamadas y resultados; auditoría conserva el cliente ejecutor;
- producción falla cerrada ante OAuth, Redis, configuración o autoridad incompletos;
- rollback preserva identidades, comandos, payloads autorizados y auditoría.

## 3. Alcance de herramientas

Lecturas de fase A: contexto, catálogo, ventas, gastos, pagos por método, cortes, conciliación,
insumos, stock, movimientos, recetas, proveedores, presentaciones de compra, historial de compras,
necesidades de compra y estado de operación.

Escrituras de fase C: propuesta de catálogo, propuesta de insumo, propuesta de receta y borrador de
compra. Quedan fuera: aplicar/rechazar propuestas como humano, confirmar/recibir/pagar/cancelar
compras, movimientos/ajustes/conteos de inventario, caja/pagos, usuarios/permisos, secretos,
configuración productiva y cualquier endpoint no enumerado.

## 4. Secuencia de implementación y tareas

### Paquete 0 — Especificación y contrato RED

- Aprobar ADR-049 y fijar versión compatible del SDK oficial de Python.
- Resolver issuer/resource/audience/scopes y quién administra clientes; MCP no emitirá tokens.
- Crear manifiesto tipado de veinte operaciones y prueba RED de paridad contra OpenAPI/runtime.
- Fijar nombres, schemas estructurados, errores, cache scope/TTL y límites.
- Evidencia: TDD-TC-481/482/483 en RED por ausencia de runtime, sin contarlos como aprobados.

### Paquete 1 — Servicio compartido y regresión REST

- Extraer `AgentToolsService` de los handlers sin cambiar contratos, guardas o resultados.
- Mantener `AgentPrincipal` como tipo distinto de usuarios humanos.
- Ejecutar las pruebas focales existentes de Agent Tools; cualquier diferencia REST es bloqueo.
- Implementar oráculo de paridad en proceso, no snapshots duplicados mantenidos a mano.

### Paquete 2 — MCP de sólo lectura

- Montar `/mcp` sólo con flag default false y Streamable HTTP stateless.
- Implementar protected-resource metadata, `TokenVerifier`, reautorización y scopes.
- Registrar las dieciséis herramientas de lectura desde el manifiesto allowlist.
- Filtrar `tools/list` por autoridad; cache privado por identidad/versión.
- Agregar límites, rate limit distribuido, timeouts, correlación y redacción.
- Probar con cliente MCP real; legacy sólo si el cliente canary lo exige.

### Paquete 3 — Identidad multibot

- Diseñar migración forward-only desde unicidad `(integration_id, profile)` a
  `(integration_id, client_key)` sin ampliar autoridad.
- Agregar alta/rotación/revocación independientes y auditoría del actor humano administrador.
- Hacer preflight, ida/vuelta SQLite y PostgreSQL, backfill estable y downgrade bloqueado con historia.
- Cambiar UI Admin sólo si se aprueba la gestión visual; entonces activar semántica, typecheck,
  build y QA visual de estados relevantes.

### Paquete 4 — Escrituras mediadas

- Registrar sólo las cuatro herramientas allowlist con `Idempotency-Key` estable.
- Reutilizar command log, hash canónico, locks y servicios existentes.
- Probar carrera/replay/fallo parcial en PostgreSQL aislado y ausencia de efectos prematuros.
- Mantener `operation_status` para timeout; no agregar callback hasta requisito separado.

### Paquete 5 — Operación, auditoría y release

- Documentar flags, issuer/resource, Redis, límites, drenado, revocación y rollback.
- Instrumentar sólo señales que respondan las preguntas de SDD §72.4.
- Ejecutar AppSec dirigido y auditoría Sol independiente con contexto fresco.
- CI ejecuta suite completa aplicable; corregir sin silenciamientos ni exclusiones.
- Preparar canary A de sólo lectura. Deploy/configuración/secretos/canary requieren aprobación
  separada; las fases B y C no se habilitan por el éxito de A.

## 5. Estrategia de pruebas

Archivos candidatos:

- `apps/api/tests/test_mcp_contract.py`: manifiesto, schemas, nombres y drift;
- `apps/api/tests/test_mcp_transport.py`: versiones, headers, stateless y límites;
- `apps/api/tests/test_mcp_authorization.py`: OAuth, matriz, revocación y cache;
- `apps/api/tests/test_mcp_reads.py`: paridad de dieciséis lecturas;
- `apps/api/tests/test_mcp_writes.py`: propuestas/borrador y ausencia de efectos;
- `apps/api/tests/test_mcp_postgres.py`: concurrencia, replay y fallo parcial;
- `apps/api/tests/test_mcp_identity_migration.py`: backfill/ida/vuelta/aislamiento;
- `tests/e2e/test_mcp_readonly_client.py`: cliente real canary;
- `tests/architecture/test_traceability.py`: IDs y relaciones.

Orden de gates:

1. pytest focal del paquete y `git diff --check`;
2. Ruff/mypy focal para backend;
3. pruebas Agent Tools REST afectadas y contrato REST/MCP;
4. SQLite/PostgreSQL sólo cuando se active persistencia, migración o concurrencia;
5. E2E con cliente MCP real y AppSec dirigido;
6. auditoría Sol R3 independiente;
7. CI completa aplicable una vez antes de integrar.

Un test escrito pero no ejecutado no es evidencia. Un push no acredita CI, deploy, migración,
configuración o producción.

## 6. Criterios de aceptación y terminado

- cadena PRD → SDD/ADR → BDD → TDD → matriz aprobada y sin IDs huérfanos;
- `/mcp` ausente con flag apagado y fail-closed en configuración productiva;
- manifiesto exacto: dieciséis lecturas y, sólo en fase C, cuatro escrituras;
- OAuth valida issuer/resource/audience/scopes y cada llamada reautoriza;
- dos bots del mismo perfil se revocan, auditan y limitan de forma independiente;
- paridad REST/MCP de resultados, errores, minimización y scope;
- PostgreSQL demuestra un solo efecto bajo replay/carrera y recuperación sin duplicados;
- migración reversible cuando no hay historia; rollback operativo preserva historia;
- límites y redacción verificados; señales responden preguntas operativas;
- gates focales, CI aplicable y auditoría Sol sin bloqueantes;
- evidencia separa local, CI, Git, despliegue, migración, canary y producción.

## 7. Afirmaciones R3 para refutación

Cada implementación debe registrar afirmación, evidencia, intento de refutación, resultado y riesgo
residual para: autoridad no ampliada; cache sin fuga; revocación inmediata en la siguiente llamada;
replay sin duplicados; fallo parcial sin efectos; paridad REST/MCP; aislamiento entre bots; ausencia
de bypass genérico; migración/rollback sin pérdida histórica. Los contraejemplos mínimos son scope
cruzado, token/catálogo obsoleto, misma key con hash distinto, ganador concurrente, crash antes/después
del commit, downgrade con historia y dependencia indisponible.

## 8. Canary y rollback

Canary: desplegar con flag apagado; configurar por aprobación separada issuer/resource y un cliente;
habilitar una sucursal/Administrador; comparar lecturas conocidas con REST; negar otra sucursal,
perfil y herramienta; observar latencia/errores/revocación. No habilitar escrituras.

Rollback: retirar primero herramientas de escritura, bloquear emisión/altas, permitir recuperación
propia durante drenado, revocar clientes, deshabilitar `/mcp` y preservar historia. Si la migración
ya tiene múltiples identidades o comandos, no ejecutar downgrade destructivo.

## 9. Estado de implementación local de fase A

Scaffold implementado en `apps/api/restaurant_os/mcp_server.py` y montado condicionalmente desde
`main.py`: MCP `2026-07-28` stateless, protected-resource metadata, JWT firmado por JWKS externo,
validación de issuer/audience/scope/expiración, dieciséis lecturas allowlist, catálogo privado con
TTL cero, reautorización persistida por identidad y reutilización en proceso de los handlers Agent
Tools. El SDK oficial 2.3.0 y sus hashes quedaron en los manifests reproducibles Python 3.12.

Evidencia local actual:

- `apps/api/tests/test_mcp_contract.py`: 8 aprobadas, incluido cliente oficial MCP 2.3.0;
- Agent Tools focal, locks y trazabilidad: 50 aprobadas en total; el caso de hash que requiere red
  se repitió con acceso autorizado a PyPI y pasó;
- Ruff focal y mypy focal: aprobados;
- PostgreSQL, migración y browser no se activaron porque este scaffold no cambia esquema,
  persistencia, concurrencia ni UI.
- auditoría Sol R3 independiente: sin P0; se corrigió el uso de `sub` no firmado en el bucket previo
  a autenticación y se endureció la descarga/configuración JWKS. La auditoría ratificó como
  bloqueantes de release los schemas abiertos, la paridad incompleta y el filtrado fino de alcance.

Pendiente antes de considerar fase A terminada: paridad exhaustiva REST/MCP para las dieciséis
lecturas y sus errores, schemas cerrados, matriz completa de perfiles/capacidades/sucursales,
allowlist/egress DNS para JWKS, rate limit posterior a autenticación por identidad OAuth, límites de
timeout y concurrencia, observabilidad/redacción dirigida, extracción formal de
`AgentToolsService` y CI completa aplicable. Continúan fuera de alcance la migración multibot de fase
B y todas las escrituras de fase C.
