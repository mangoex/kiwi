## Resultado

La implementación agrega cajero canónico al turno, corte `DRAFT -> COUNTED -> FINALIZED`, snapshot
financiero calculado por Python, asociación global append-only de pagos/movimientos, historial
redactado y reapertura exclusiva de Dueño mediante compensación. Incluye migración `0041`, contratos
JSON Schema estrictos, endpoints versionados, panel POS, auditoría y métricas sin importes ni PII.

La matriz queda en `Probado`, no en `Implementado`: PostgreSQL real se ejecutará en el CI protegido
del PR y la QA visual sigue omitida porque el runtime no encontró un navegador conectado. Ninguna de
esas omisiones se presenta como evidencia verde.

## Hallazgos corregidos durante auditoría

- contrato legacy de turno incompatible con `cashier_user_id` nullable;
- cursor HTTP no reenviado y filtros sin validación de estado/rango;
- checks de modelos distintos de la migración y esperado negativo inválidamente rechazado;
- TC-117 inicialmente sólo ejecutaba Alembic y no probaba concurrencia;
- parser POS rechazaba cortes DRAFT válidos con componentes nulos;
- schemas incompletos y respuestas list/detail/reopen/compensation sin validación runtime;
- conflicto de reapertura podía filtrar `IntegrityError` y finalize podía dejar evidencia no probada;
- cambio de sucursal conservaba detalle/intenciones anteriores;
- telemetría ausente/duplicada para algunos comandos.

## Límites y promoción

No se usó PostgreSQL productivo, `DATABASE_URL`, Easypanel, deploy ni migración productiva. La
promoción exige CI PostgreSQL verde. El despliegue, snapshot, `alembic upgrade 0041_user_cash_cuts`,
canary financiero y QA visual productiva requieren autorización operativa separada.
